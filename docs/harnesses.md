# Adding an engine to Silos

Silos runs AI coding agents. The program that actually does an agent's work
is called the agent's **engine** (in the code: its **harness**). Today Silos
drives two: **Claude Code** and **OpenCode**. This document is for someone
who has never seen Silos and wants to add a third, for example Codex CLI.

What that takes: **one folder**, `server/src/harnesses/<id>/`, whose
`index.ts` exports a `Harness` object (the types are in
`server/src/harnesses/contract.ts`), **one line** in
`server/src/harnesses/index.ts` that registers it, and **one conformance
fixture** in `server/test/conformance/`. Nothing else in the server or the
web has to change: the rest of Silos asks the registry what each engine is
and can do. [§3](#3-registration-touchpoints) is the short list; a few
things are honestly not generic yet, and [the known limits](#known-limits-for-a-third-engine)
names them.

The smallest complete example is the test-only fake third engine,
`server/test/fixtures/fake-harness.ts` (about 100 lines). It is registered
next to the two real engines in `server/test/harness-fake-engine.test.ts`,
which boots the real server around it with no change under `server/src`.
Read it alongside this document.

```
server/src/
  index.ts                  the composition root; imports the registration list and, as everywhere, may name only the fallback (Claude Code) directly
  compose.ts                boots every registered harness (bootHarnesses)
  session-index.ts          the one index of sessions; names no engine
  chat-service.ts           routes a chat turn to its engine
  console-open.ts           the generic console open, for an engine with no hooks of its own
  harness-descriptor.ts     what GET /api/harnesses tells the web about each engine
  harnesses/
    contract.ts             what an engine provides (read this first)
    registry.ts             the registry and every lookup; imports nothing at runtime
    index.ts                the registration list: one registerHarness line per engine
    fence-rules.ts          the neutral vocabulary of the territory fence
    claude-code/            Claude Code (the fallback engine)
    opencode/               OpenCode
web/src/lib/
  harnesses.ts              the one web module that knows engine descriptors
  harnesses.seed.json       a copy of the server's answer for the built-in engines
```

A few words used below:

- **user / operator**: the person running Silos. Comments in the code call
  them "the owner".
- **console**: an engine's own interactive terminal UI, which Silos runs in a
  tmux session and shows in the browser. OpenCode's is a **TUI** (text user
  interface) with its own small HTTP server.
- **headless turn**: a chat turn Silos runs without a console, when the user
  types into Silos' own composer or an automation runs.
- **pin**: the model or provider the user chose for one conversation, which
  Silos stores and applies to that conversation's next run.
- **sealing an id**: recording, once it is safe to trust, which agent and
  which console a newly minted session id belongs to.
- **fence** (territory): per-agent deny rules Silos generates (credentials,
  other agents' state, private paths). They are written in Claude Code's
  rule grammar, `Tool(pattern)`, and each engine translates them.
- **the fallback**: the one registered engine that owns every session id no
  other engine claims, and runs every agent with no `framework` field. It is
  Claude Code. A new engine is never the fallback.

## 1. What a harness is

Everything in this section is in `server/src/harnesses/contract.ts`, which
holds types plus one helper, `isFileBacked`. The lookups (`harnessOf`,
`harnessForId`, `harnessById`, `fallbackHarness`, `registeredHarnesses`…)
are in `server/src/harnesses/registry.ts`.

**`caps`** say what your engine can do: `compaction`, `subagents`,
`skills`, `thinking`, `costFromHarness`, `permissionsAsEvents`,
`sendToConsole`, `outputStyles`. Declare the truth. They reach the web in your descriptor
(§1.8). One is checked: an engine with `permissionsAsEvents: true` must
provide the `answer` server hook (§1.7). Another is enforced at
registration: `outputStyles: true` comes with an `outputStyles(cwd)` lister
(the styles a conversation in that folder can answer in, read-only) and the
style must reach both your chat turn and your console (`LaunchSpec.outputStyle`);
`false` means the cockpit's style field is never offered nor sent.

**`traits`** (`HarnessTraits`):

- `deletion: 'trash' | 'hide'`. `'trash'` means your sessions are files
  Silos moves to `~/.silos/trash/`, which needs a file-backed reader (§1.2;
  conformance checks this). `'hide'` means "delete" hides the session on
  Silos' side and your engine's data is never written. A new engine must
  say `'hide'`: `'trash'` is the fallback's alone (see the known limits in
  §3), and `registerHarness` refuses it on any other engine. The trash route
  (`POST /api/sessions/:folder/:id/trash` in `server/src/server.ts`) reads
  this trait.
- `handover: boolean`. Your console and your headless turns write the
  **same** session. Then Silos closes a live console before a headless turn
  on it (`server/src/console-handover.ts`), and a started conversation may
  switch between console and chat in the UI.
- `consolePinsModel: boolean`. A model picked inside your console arrives as
  `meta.requestedModel` and becomes the conversation's pin
  (`server/src/pin-follower.ts`), through your `requestedModelPin`.
- `agentStateDirs: string[]`. Entries your plugin writes under the agent's
  state directory, kept out of the agent's "produced" files
  (`server/src/context-service.ts`).

**`providers`** (`HarnessProviderRules`):

- `kinds`: the provider kinds you can run, from `'claude-account'`,
  `'anthropic-compatible'`, `'harness-provider'` (a key for a provider your
  engine already knows) and `'harness-native'` (your engine's own login).
  The neutral `'default'` provider is always allowed. A `harness-*` provider
  runs only on the engine it was created for. `providerHarnessError` in

  validates and stores providers; **applying** the resolved provider
  (`LaunchSpec.provider`, and the key in the env) is your launch's job.
- `export` (optional): `{ target, snippet(p) }` for Settings › Providers
  "Copy config": the `?target=` value of `GET /api/providers/:id/export`
  and the config fragment for your engine, never with the key.

`PermissionConfig` (`server/src/harnesses/fence-rules.ts`): per tool kind
(`read`, `edit`, `bash`), one action or a map of glob to action.
Settings › Territory uses it, through `fencePermissionFor` and
`fenceSummary`, to say what the fence really denies on your engine. It is a

`server/src/harnesses/opencode/fence.ts` are two real dialects, and the
fake's `passThrough` is the smallest.

### 1.2 `HarnessReader`: reading your sessions

Silos lists, opens and follows conversations through one index,
`SessionIndex` (`server/src/session-index.ts`). It knows nothing about any
engine. It merges **readers**, one per engine, and routes each session id to
the reader that owns it. Your `boot()` returns your reader as
`runtime.reader` and `compose.ts` adds it to the index
(`index.addReader`).

Required members:

| Member                                                                     | What it does                                                                                                                                                                                             |
| -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `harness`                                                                  | your `HarnessId`                                                                                                                                                                                         |
| `ownsId(id)`                                                               | true for ids your engine minted. Must agree with your `Harness.ownsId` (conformance checks it against `harnessForId`)                                                                                    |
| `init()`                                                                   | load from disk or DB. Afterwards `list()` and `getMeta()` answer from memory                                                                                                                             |
| `list()`                                                                   | every session you know, as `SessionMeta` (`server/src/types.ts`), each stamped with `harness: '<your id>'`                                                                                               |
| `getMeta(folder, id)` / `getContext(folder, id)` / `readTurns(folder, id)` | one session's metadata, its context-column data, and its transcript                                                                                                                                      |
| `refresh(folder, id)`                                                      | re-read one session; return its meta, or `null` if it is gone                                                                                                                                            |
| `remove(folder, id)`                                                       | **hide** it (Silos never deletes another program's data). Return `false` when you never knew the id; the index then emits nothing. Return `void` if you cannot tell, and the index announces the removal |
| `watch(cb)`                                                                | call `cb(ref, 'created' \| 'updated' \| 'removed')` when something changes that the index cannot see by itself                                                                                           |

**The index emits, you don't.** `SessionIndex` turns your answers into its
`'session'` and `'removed'` events (the server forwards them to the browser).
Your `refresh()` only returns the meta. `watch()` is for changes that happen
without anyone calling `refresh()`: a background poll, a database row that
appeared.

Optional members:

- `hidden(folder, id)`: the session is known by id (so `getMeta` answers) but
  is not a conversation. **Your own `list()` must leave hidden ids out; the
  index does not filter them.** The index only skips the `'session'` emit on
  `refresh()`, and `refresh()` still returns the meta. Claude Code uses this
  for "bookkeeping-only" transcript stubs.
- `usageRecords(folder, id)`: what a conversation used, for Usage — its
  assistant records and its child sessions', each
  `{ id, at, model, tokens, costUsd, session }` (`UsageRecord`), one per
  message id within a file, priced by YOUR table (`costUsd: null` for a
  model without a price). The price travels here so no neutral module names
  an engine's price table. Absent: Usage says «not measured on <label>» for
  your sessions and never invents tokens. Claude Code's is
  `harnesses/claude-code/usage-records.ts` (incremental by byte offset).
- `silosOwnUsage(sinceMs)`: records of what Silos itself ran through your
  engine outside any conversation (Claude Code: the titler's one-shot turns
  in their tmp folders) — Usage's «Silos itself» row. Absent: none.
- `flush()` / `stop()`: persist a cache on shutdown, stop timers. The index's
  `flushCache()` and `stopHeartbeat()` call them for every reader.
- `isReady()`: your own readiness. **Only the fallback reader's** is
  consulted: `SessionIndex.isReady()` (`server/src/session-index.ts:42`)
  asks the fallback and nobody else.

How an added reader is started, in `SessionIndex.init()`
(`server/src/session-index.ts:53-62`):

- Added readers are initialised first, in registration order, and the
  fallback last.
- If an added reader's `init()` throws, the index **catches and logs** it
  (`[session-index] <id> reader init …`, line 56) and carries on, so a broken
  engine never keeps the others from loading. Only the fallback's failure
  rejects `index.init()`.
- An added reader's `watch()` is subscribed only **after** its `init()`
  (line 57), so signals fired during `init()` reach nobody.

Ids route by "the first added reader whose `ownsId(id)` is true, otherwise
the fallback". A row the fallback lists under an id another reader owns is
dropped from `allSessions()`, so the list always agrees with the routing.

**`FileBackedReader`.** If your sessions are files on disk (Claude Code's
JSONL transcripts are), also implement `root`, `transcriptPath`, `sessionDir`
and `listSubagents`, and `isFileBacked(reader)` will return true. The routes
that serve a session's own files (images inside a transcript, subagent
transcripts) work only for file-backed readers. For any other reader they
answer "no transcript file". OpenCode keeps its sessions in SQLite, so it is
not file-backed.

### 1.3 `HarnessConsole`: launching the console

```ts
interface HarnessConsole {
  idDiscovery: 'silos-chosen' | 'reported-by-plugin'
  newSessionId?(): string
  command(spec: LaunchSpec): string[] // argv
  env(spec: LaunchSpec): Record<string, string>
  dialogOnScreen?(screen: string): ConsoleDialog | null
}
```

- `idDiscovery`. `'silos-chosen'` means Silos picks the new session's id and
  passes it in (Claude Code takes `--session-id <id>`). `'reported-by-plugin'`
  means your engine mints its own id and a small Silos plugin running inside
  it reports that id back. OpenCode does this: `plugin-opencode/silos.ts`
  writes a birth marker, and `server/src/harnesses/opencode/registrar.ts`
  seals it.
- `newSessionId()`. **Required in practice for a `'silos-chosen'` engine
  that is not the fallback.** The generic console open mints a new
  conversation's id with it; the default is a bare UUID, which no
  non-fallback `ownsId` claims, so the new session would route to Claude
  Code. The fake returns `fake_<uuid>`. Conformance checks that a
  non-fallback, silos-chosen engine declares it and that
  `harnessForId(newSessionId())` is your id.
- `command(spec)`: the argv, for a new session or a resume
  (`spec.resumeId`).
- `env(spec)`: the environment.
- `dialogOnScreen(screen)`: optional. Whether your TUI shows a dialog
  (`'trust' | 'permission' | 'question' | 'plan'`) on this captured screen.
  Every prompt Silos types into a console asks it first, because the Enter
  would pick the highlighted option. Be conservative: only your TUI's own
  known markers count, and an unknown screen is `null`. Leave it out when
  your engine takes prompts over its own API (OpenCode's `sendText`).

`LaunchSpec` carries the agent, cwd, console key, resume id, theme,
permission mode, role append, fence, resolved provider, model, the role's
skills plugin (`rolePlugin` — `agent-state/<id>/plugin` when the role HAS
skills; Claude Code passes it as `--plugin-dir` / SDK `plugins: local`,
OpenCode appends `<dir>/skills` to its config's `skills.paths`; spec
2026-11-03-role-skills), and the env Silos built (Vault secrets, agent
state, `SILOS_SESSION_ID`). The console's turn token (`SILOS_TURN`,
`server/src/live-turns.ts`) is not yours to build: `TerminalService` mints
it for every console it spawns and adds it to the same env file.

**The generic open.** With no `openSession`/`openNew` hooks (§1.7),
`POST /api/console` goes through `server/src/console-open.ts`: for a
silos-chosen engine it builds a `LaunchSpec` from the same cascades a
built-in console uses (provider, permission mode, model, fence, append,
env), then hands `command(spec)` and `env(spec)` to
`TerminalService.ensureConsole`. A resume reattaches to a live console or
relaunches under the session's own id; a new conversation is born under
`newSessionId()` and Silos records who gave birth to it. The agent's
waiting console is reused while nothing has been typed into it (still
live, its session not listed yet, an id of your engine), the same rule
both built-ins' own `openNew` hooks follow, so "New conversation" twice
starts one process, not two. A
`'reported-by-plugin'` engine with no hooks gets an honest 400, "`<label>`
has no console in Silos yet": seeing the reported id needs your own hooks,
as OpenCode has.

**Secrets never go in argv.** Provider keys and passwords go in the env,
which the terminal service writes to an **env file** that the launcher
sources and deletes (`writeEnvFile` in `server/src/terminal-service.ts`). The
conformance suite checks that `command()` never contains the provider key or
a password. Env names must be shell-safe (`[A-Z_][A-Z0-9_]*`).

### 1.4 Headless: chat turns without a console

`Harness.headless(ctx)` returns a `HeadlessEngine`, or `null` when it is not
wired:

```ts
interface HeadlessEngine {
  send(agent: Agent, input: ChatSendInput): AsyncGenerator<ChatEvent>
  cancel(turnId: string): Promise<boolean>
  isInflight(turnId: string): boolean
  isSessionActive(sessionId: string): boolean
}
```

`ChatService` (`server/src/chat-service.ts`) builds one engine per
registered harness in its constructor and routes each turn by the agent's
engine (`harnessOf(agent)`). `ctx` holds:

- `deps`: ChatService's own dependencies, a live object (read fields when
  you use them, not once).
- `options`: your runtime's `headlessOptions` (§1.5), or `undefined`.
- `hooks` (`ChatTurnHooks`): `providerFor(agent, pinnedId)` (the provider
  cascade with fallback applied), `appendFor(agent)` (the role prompt),
  `onRateLimit` and `onErrorText` (the fallback bookkeeping), and `emit`.

**You must export `input.turnToken` as `SILOS_TURN`** in your process's env
(next to `SILOS_SESSION_ID`): `ChatService.send` mints it for every turn and
every bearer write the agent makes from that turn names it — without it the
agent's writes are refused. Reserve the name so a
Vault entry can't shadow it.

**You must call `ctx.hooks.emit(agent.id, ev)` for every event your turn
yields, in order.** `ChatService` turns it into its `'chat-event'`, and the
automation runner (`server/src/resident.ts`) learns about turns only from
that event: skip it and automations on your engine never see their turns
finish. Conformance checks it when your fixture provides `headless` (§4).
`ChatEvent` is in `server/src/chat-types.ts`.

Real examples: `server/src/harnesses/opencode/headless.ts` (one
`opencode run --format json` child per turn) and
`server/src/harnesses/claude-code/headless.ts` (one Claude Agent SDK
`query()` per turn). The fake's `headless` yields one text delta and a
done event.

### 1.5 `boot`: your runtime

`compose.ts` `bootHarnesses(ctx)` calls every registered harness's `boot()`
once, in registration order, right after the composition root
(`server/src/index.ts`) has built the agent registry and the stores. The

`registry`, `asks`, `muted`, `ephemeral`, `modelCatalog` (false when
`SILOS_NO_MODEL_CATALOG=1`: return no `modelFetcher`) and `log`.

`HarnessRuntime`, every member optional:

| Member                | Used for                                                                                                                                                                                                                                                                                                                                                 |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `reader`              | your `HarnessReader`, added to the index. The fallback's reader becomes the index's fallback; `bootHarnesses` throws if the fallback boots none                                                                                                                                                                                                          |
| `ownership`           | `{ agentOfDb(id), isContested(id) }`: who a session belongs to by your engine's own storage (OpenCode: which agent's database holds it). Merged for `SessionOwners`: `agentOfDb` takes the **first non-null** answer across engines; `isContested(id)` is asked **only of the engine that owns the id** (`harnessForId`), never "any engine contests it" |

| `headlessOptions`     | handed to your `headless(ctx)` as `ctx.options`                                                                                                                                                                                                                                                                                                          |

The root awaits `Booted.ready()` right after booting, before any start phase runs                                                                                                                                                                                               |

Return `{ serverOptions?, stop? }`: `serverOptions` reaches your server hooks as `ctx.options` (OpenCode: its console registrar and probes)                                                                                                                                                                             |

index, terminals, births, native and conversation-prefs stores, and
`root`/`muted`/`ephemeral`. Every `stop` runs on shutdown.

**Register before boot.** `ChatService` and `HarnessService` read the
registry in their constructors, the server builds each engine's hooks on
first use, and `ModelCatalog` snapshots the registry the first time it is

registration list is imported on the first line of `server/src/index.ts`,
so a `registerHarness` line in `server/src/harnesses/index.ts` is always in
time.

### 1.6 `versions`: the Settings row and the updater

`Harness.versions({ run, now, options })` returns `HarnessVersions`.
`HarnessService` (`server/src/harness.ts`) walks the registry for
`GET /api/harness` and `POST /api/harness/update`:

- `version()`, `compat()`, `updateCommand()` (`[cmd, args]`) and
  `updateLabel` (the words the update error uses, for example
  `'opencode upgrade'`) are required.
- **`compat()` is your compatibility verdict** (no
  compatibility with older engines). Declare the lowest version Silos
  runs in your adapter and build the verdict with `minimumVerdict`
  (`harness-run.ts`): `ok`, `outdated` or `missing`, with what is
  installed, what is needed, the exact update command, what it `refuses`
  (`console`, `chat`) and its one-line `message`. `HarnessService.refusal`
  gates every console open (`POST /api/console`, 409 `{ error, compat:
true }`) and every chat turn (`ChatService` `compatGate`) on it; Home
  folds every engine in use that is not ok into ONE Needs-you row
  (`inbox.ts` `engineCompatRow`, door Settings › Account), and Settings
  says the line under your version. Never tolerate an older binary with a
  fallback or a capability probe: refuse it. Claude Code adds `ahead` (a
  CLI newer than the Agent SDK it is paired with).
- **The fallback must provide `primary()`**: the top-level rows — the one
  binary its consoles and chats run, and the client library it ships
  (`library`, or null). Without it `status()` throws.
- **A non-fallback engine provides `other()`** for its row in `others[]`.
  Without it there is no Settings row, though an update can still target it.
- `invalidate()` drops a cached version after an update.

Run every process through `ctx.run` (`server/src/harness-run.ts`), so tests
never spawn your binary.

### 2.3 `harnesses/claude-code/`

Claude Code is the original engine and the fallback. It differs in four
ways:

1. **Silos-chosen ids, and the fallback's form.** A new console gets
   `--session-id <key>`, a bare UUID (the fallback owns every unclaimed id,
   so it needs no `newSessionId`). Its argv is built by
   `server/src/harnesses/claude-code/console.ts`.
2. **A file-backed reader.** `ClaudeReader`
   (`server/src/harnesses/claude-code/reader.ts`) parses the JSONL transcripts
   under `~/.claude/projects/<folder>/<id>.jsonl` incrementally, with a
   persistent parse cache (`CACHE_VERSION`, see §5). Its `deletion` is
   `'trash'`.
3. **The fallback reader.** Its `boot()` returns the reader that
   `bootHarnesses` makes the index's fallback. Tests build the same index
   with `claudeSessionIndex(...)` from that file.
4. **A watcher feeding the index.** `afterServer` starts
   `server/src/harnesses/claude-code/watcher.ts`, which watches the transcript
   directory and calls `index.refresh(folder, id)` / `index.remove(folder, id)`.
   A reader whose source changes on its own needs something like this, or
   uses its own `watch()` signals.

**One Claude Code.** Consoles and chat turns run the SAME
binary: the `claude` on PATH (`binary.ts` `claudeOnPath`, the PATH entry
itself, never its realpath, so a native install's `claude update` or
auto-update moves both). A `claude` in the native installer's directory
(`~/.local/bin`) is found even when the PATH that started Silos leaves it
out (`binary`, `engine-path.ts`). Every Agent SDK query gets it as
`pathToClaudeCodeExecutable` at the SDK boundary (`sdk.ts`, `models.ts`
via `withClaudeExecutable`); the SDK's bundled platform binaries are never
run. The SDK npm package is the client library only, pinned in
`server/package.json` and paired with one Claude Code release (its
package.json `claudeCodeVersion`, 0.3.N ↔ 2.1.N). **Minimum** = that
paired release (`version.ts` `claudeCompat`): older → `outdated`,
consoles and chats refused with `claude update`; a newer 2.1 patch →
`ahead`, chats keep running (the control protocol is negotiated — optional
fields «older CLIs ignore», capabilities «advertised on system/init»,
`sdk.d.ts`) and the line names the matching SDK to move Silos to; a newer
line (2.2.x) → `ahead` too: nothing is refused (an auto-update must never
stop automations and wakes), the line warns that Silos is not yet verified
with it. Upgrading the SDK =
`npm install -w server --save-exact @anthropic-ai/claude-agent-sdk@0.3.N`
(exact: the pin is the pairing).

## 3. Registration touchpoints

1. **Your folder**, `server/src/harnesses/<id>/`, whose `index.ts` exports a `Harness`
   (contract.ts). Not the fallback: declare `ownsId`. Declare `traits`, `providers`,
   `ui`, `fencePermission`; add `boot`, `headless`, `versions`, `server`, `models` for
   what your engine has. What you leave out has an honest neutral default (§1).
2. **One line** in `server/src/harnesses/index.ts`: `registerHarness(yours)`.
3. **Tests**: `server/test/conformance/<id>.fixture.ts` (the conformance suite finds it
   and fails until it exists) and your own `server/test/<id>-*.test.ts`.

That is all, literally: with a throwaway third engine added this way (its folder, the
`import` + `registerHarness` lines in `harnesses/index.ts`, its fixture, and nothing else)
the full server and web suites pass. Tests that check the engine list compare against the
registry (`server/test/helpers/built-ins.ts`: `registeredIds()`, and `quotedIds(harnessIds())`
for the 400 texts) while still pinning the built-ins first, in order; refusal tests use
`not-an-engine` as their unknown id, never a plausible engine name. The web learns about your engine from `GET /api/harnesses`; an engine it
has no descriptor for is shown with a conservative descriptor (never as Claude Code).
Optional: add your descriptor to `web/src/lib/harnesses.seed.json` for first paint
before the server answers; the server test checks the seed never drifts.

### Still outside the folders (on purpose)

- TerminalService's built-in console command and lock scan are Claude Code's; any other
  engine passes `command` (the generic console open does).
- Claude-named features (accounts, account load, titler, peers, Claude settings) are
  features built on Claude Code, not seams.
- `ChatDeps.queryFn` is Claude Code's SDK seam for tests.
- Four top-level modules serve any engine and stay neutral; none names an engine in code
  (the name ratchet, §4):
  - `asks-store.ts`: the permission-ask file protocol (`agent-state/<id>/asks/`, replies
    under Silos' data dir) that Needs you, Territory and the answer route read. Today only
    OpenCode's plugin writes it; an engine with `caps.permissionsAsEvents` may reuse it.
  - `console-palette.ts`: answers a TUI's OSC 4 palette queries for a console launched
    with `skin.palette` (`TerminalService.ensureConsole`); whoever passes a skin gets it.
  - `pin-follower.ts`: driven by `traits.consolePinsModel`; the id dialect is the
    engine's own `requestedModelPin`.
  - `console-handover.ts`: driven by `traits.handover`; its log names the session's engine.

### Known limits for a third engine

These are not generic yet. Each is a named follow-up; until then a third
engine either lives with it or edits the place named.

- **Typed model ids are not validated.** For an engine with
  `ui.models: 'none'`, the model field accepts whatever the user types
  (trimmed); the server does not check it against anything.
- **`deletion: 'trash'` is the fallback's alone.** The trash route
  (`POST /api/sessions/:folder/:id/trash`) moves files with
  `SessionStore.trash` under Claude Code's root, with its holder scan and
  lineage. `registerHarness` throws on a non-fallback engine declaring
  `'trash'`, and conformance asserts the same; declare `'hide'`.
- **`'provider-model'` means OpenCode's naming.** The web helpers behind
  `ui.models: 'provider-model'` (`web/src/lib/providers.ts`
  `providerModelId`, `gatewayProviderAlias`; `web/src/lib/runs-on.ts`)
  write a stored model as `<providerId>/<model>` and a Silos gateway as its
  own `silos-<id>` provider, the way OpenCode's launch names them
  (`harnesses/opencode/launch.ts` `providerLaunch`). A third engine that
  declares `'provider-model'` is shown with that naming; its launch should
  name models the same way, or declare `'none'`.
- **A provider message with no engine at hand names every engine.** Neutral
  provider refusals name the engine that owns the provider
  (`engineProviderLabel` in `server/src/harnesses/registry.ts`). Where the
  provider's engine is not known yet (the provider-id format on a `PATCH`,
  "providerId/harness are only for … providers" on an Anthropic-compatible
  body), they name every engine that owns `harness-*` providers: "OpenCode"
  today, "OpenCode or `<yours>`" once yours does.
- **Plan proposals are Claude Code's only.** A conversation's plan-mode
  plan (`ToolUseDetail.plan`, `SessionContext.planMode`: the sheet in the
  transcript, the column row, a proposed plan lighting `pendingAsk`) is read
  from Claude Code's `ExitPlanMode` tool use (verified on CLI 2.1.316,
  fixture `plan-mode.jsonl`). OpenCode's plan mode is a primary agent
  (`--agent plan`, no edits) with no proposal/approval record to read, so it
  shows nothing — an engine that writes one fills the same two fields.
- **`isReady()` is the fallback's only** (§1.2): the index does not wait for
  your reader.
- **A `'reported-by-plugin'` console needs its own hooks** (§1.3); there is
  no generic way to learn an id your engine reports later.

## 4. Tests

- **Layout.** Tests stay flat in `server/test/`, named after the engine:
  `server/test/<id>-*.test.ts` (for example `opencode-reader.test.ts`,
  `opencode-fence.test.ts`, `claude-code-parser.test.ts`). Shared fixtures
  are in `server/test/fixtures/` and helpers in `server/test/helpers/`.
  `server/test/setup-harnesses.ts` imports the registration list before every
  server test, so tests see the same registry production does.
- **Conformance** (`server/test/harness-conformance.test.ts`). It loads
  every `server/test/conformance/*.fixture.ts` by glob; the fixture shape is
  `ConformanceFixture` in `server/test/conformance/contract.ts`, and
  `server/test/conformance/fake.fixture.ts` is the shortest to copy. The
  suite fails while a registered harness has no fixture. The same
  assertions run over every engine:
  - registered under its id, with a label; all 8 caps declared as booleans
  - argv carries neither the provider key nor a password, new or resumed;
    env names are shell-safe
  - a non-fallback, silos-chosen console declares `newSessionId`, and the
    id it mints routes to it
  - `deletion: 'trash'` only over a file-backed reader, and only on the fallback
  - `caps.permissionsAsEvents` implies an `answer` server hook
  - `traits.consolePinsModel` implies `requestedModelPin`
  - at least one provider kind; every required UI fact declared; a
    relative model-catalogue file
  - if the fixture provides `headless`: every event a turn yields is
    emitted to `hooks.emit` too, in order, under the agent's id
  - exactly one fallback; no two non-fallback engines claim the same id
  - reader ids are disjoint across engines and agree with `harnessForId`
  - `list()` returns only your harness's metas; one `remove()` gives exactly
    one `'removed'`; `remove()` of an unknown id answers as declared;
    `list()` never includes a `hidden()` id; `isFileBacked` is what you
    declared
- **Boundary** (`server/test/harness-boundary.test.ts`). It keeps the
  structure honest. Imports are read from a real TypeScript parse
  (`server/test/helpers/module-specifiers.ts`), never a regex. Engine
  folders are read from disk, so yours is covered without an edit:
  - no engine folder imports another engine folder (every ordered pair)
  - only the registration list imports an engine's `index.ts`, and only
    `server/src/index.ts` imports the registration list
  - `harnesses/registry.ts` imports nothing at runtime, and `server/src`
    has no runtime import cycle
  - `server/src/session-index.ts` names no engine, and nothing outside
    `harnesses/claude-code/` imports the Claude Agent SDK
  - no registered engine id is spelled as a string literal outside
    `harnesses/`; in `web/src` the seed is the only file
    that names one. Read ids from the registry or the descriptor instead.
  - the **name ratchet**: outside its own folder, no code word (identifier,
    string, template chunk, JSX text; comments are free, read by
    `codeWords` from the same parse) names a non-fallback engine, in any case
    (`opencode`, `OpenCode`, `opencodeModelId`), in `server/src` or
    `web/src`. The registration list is the one exception. What such code
    knows belongs in your folder, a `Harness` member or a descriptor fact.
- **Gates**, run from the repository root:

  ```
  npx vitest run --root server
  npx vitest run --root web
  npm run typecheck
  ```

  Read the whole summary, not just a grep for "passed".

## 5. Rules

- **Dependency direction.** Your folder imports `../registry.js` and neutral
  top-level modules, never another engine's folder and never
  `harnesses/index.ts` (the registration list). Neutral modules read engines
  through the registry and your declared facts, never by name.
  `server/src/session-index.ts` imports no engine. Read the registry inside
  functions, never in a top-level constant: it is filled when the
  registration list is evaluated.
- **Never write the engine's own data.** Silos only reads sessions it did not
  create. Deleting one means hiding it (OpenCode) or moving it to Silos'
  trash, `~/.silos/trash/` (Claude Code). It never modifies the engine's
  database, transcripts or config files — three documented exceptions,
  each keeping every other key and entry:
  - a folder's `.claude/settings.local.json` — the capability states, the
    switches of what a folder loads and the starting set — through ONE
    writer (`harnesses/claude-code/local-settings.ts`: contained `.claude`,
    a home folder refused, a corrupt or non-object file refused untouched,
    atomic, git-ignored);
  - the user's own `~/.claude/settings.json`, through ONE writer
    (`harnesses/claude-code/settings.ts` `editUserSettings`: a file it
    can't read, that isn't JSON or isn't an object refused untouched;
    atomic, written through a symlink; re-read right before the rename and
    the change re-applied if it moved). Its callers: transcript retention,
    Silos' own hooks in and out, push notifications and the checklist (each
    after a prior copy), and the «This machine» line of a Tools row
    (`loads/machine.ts`) — ONLY on the owner's click that names the machine,
    never at a birth, a timer or a click on another place; no copy, the
    same switch undoes it. The extra logins under `claude-accounts/` follow
    that file (`accounts.ts`), and the switch's answer names any that did
    not. A machine head's «off» (what a Claude account sends, as a whole)
    is refused unless the click confirmed its sentence;
  - OpenCode's global `~/.config/opencode/opencode.json(c)` — only
    `mcp.<name>.enabled`, on the owner's click of its «This machine» line
    (`harnesses/opencode/global-config.ts`): written only while the file is
    strict JSON (comments, not JSON, not an object, an entry of another
    shape → refused, named, untouched), atomic through a symlink, re-read
    before the rename, inside the seal's own-edit hooks (the seal watches
    that file).

  What Silos keeps for the agent and conversation places (and OpenCode's
  project place) is never written into an engine file: it rides the
  launch — Claude Code's flag-tier `--settings` / `Options.settings`,
  OpenCode's `OPENCODE_CONFIG_CONTENT` — merged after the fence and
  through the engine's allowlist, at the switch AND at every launch:
  Claude Code `loads/launch-entries.ts cleanEntries` (the keys below in
  their shapes; `permissions`, `hooks`, `env`, a URL deny… dropped),
  OpenCode `cleanOpencodeEntries` (`mcp.<name>: {enabled}` and
  `permission.skill.<name>: "deny"`, merged into the fence's
  `permission`, never over it). A heartbeat takes only what removes.

  Only keys Claude Code's settings schema documents: `enabledPlugins`
  (`<name>@<marketplace>`: `false`, and `true` where it must override a
  wider `false` — the project over the machine or the repository's file,
  both at the machine as `claude plugin enable|disable --scope user` writes
  them; `<manifest name>@synced` for a plugin a Claude account sends),
  `deniedMcpServers` (`{serverName}` entries: a plugin's server, one of
  `~/.claude.json`, a `claude.ai <Name>` connector), `disabledMcpjsonServers`,
  `skillOverrides` (`name-only` · `off`, and `on` where it must override),
  `syncClaudeAiPlugins`, `syncClaudeAiSkills`, `disableClaudeAiConnectors`
  (each only in its «off» value) and `claudeMdExcludes` — the same key at
  every place (spec scopes §3), whichever carrier holds it. A key of another shape than its switch expects is
  refused, named. `~/.claude.json`, an extra login's file by hand, the
  repository's `.claude/settings.json`, managed settings and claude.ai are
  never written. If
  your engine needs config, generate it into Silos' own data directory or
  pass it through the env, as OpenCode's `OPENCODE_CONFIG_CONTENT` does.

- **Environment names.** Anything Silos itself passes to your processes is
  named `SILOS_*` (`SILOS_AGENT_ID`, `SILOS_SESSION_ID`, `SILOS_PROVIDER_KEY`,
  `SILOS_AGENT_STATE`…). Your engine's own variables keep their own names.
- **`CACHE_VERSION` discipline.** If your reader persists a parse cache, give
  it a version constant and bump it **only** when a cached shape changes. Keep
  a one-line history of every bump next to the constant, as `CACHE_VERSION`
  in `server/src/harnesses/claude-code/reader.ts` does. A stale cache restored
  as-is silently loses data; an unnecessary bump re-parses every session on
  the next start.
