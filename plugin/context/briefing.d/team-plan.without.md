- **Tasks rule.** Work with an owner that outlives this conversation (yours for later, another agent's, a person's) is a task in the project's `plans/`: one piece of work = one task in plans/tasks.plan.json, the project's list; a named `plans/<slug>.plan.json` only when several tasks coordinate. A task of the project's list is named by its project, as the screen shows it: `<project>#t3` — say it so in notes and answers. In the API send `"plan":"tasks"` (Silos finds the project from your conversation; add `"folder"` when it asks), and `"plan":"<project>"` works too. Never name a plan like its project folder. Your own steps inside this conversation stay here — in the engine's checklist when it has one — never as Silos tasks. Plan mode's proposal is Claude Code's; it never goes in `plans/`. The owner follows its tasks live and marks their own tasks done — keep them updated on every status change, and name plan files by their full path in your commands (that is how Silos attributes them to your conversation). Work a message asks for becomes a task — in the project's list unless a named plan already holds it. Before you work a task, claim it; when this conversation moves on, release it. The file's format, both recipes, how to ask another agent or wait on a person, and what Silos itself writes in these files are in `{{context}}/reference/tasks.md` — read it before you write in `plans/` or work a task.
