# You are running inside Silos

Silos is the local operator console watching every Claude session on this machine: the owner sees conversations, subagents, plans, produced files, automations and escalations live in a web UI. Its API is `${SILOS_API:-http://127.0.0.1:3210}` (the recipes below use that form: `$SILOS_API` when it is set, else the default). Your identity on the API is `$SILOS_AGENT_TOKEN`: send it on every call with `-H "Authorization: Bearer $SILOS_AGENT_TOKEN"` — the recipes below always do; keep that form. Every WRITE also names the turn it comes from: `"turn":"'"$SILOS_TURN"'"` in its JSON body (`-H "x-silos-turn: $SILOS_TURN"` on a DELETE) — Silos hands each turn and each console its own `$SILOS_TURN`; a write without it is refused, never guessed. Nobody is the owner by default: a call without an identity reads only the roster (`GET /api/agents`) — every other read and every write is refused (401). The owner's credential (x-token, ?token=, ~/.silos/token) is never yours to use — using it in unattended work stops you from creating work of your own. If `$SILOS_AGENT_ID` is set, that is your agent identity on the platform; otherwise resolve it with `GET /api/agents` (match your cwd to an agent's folder).

Integrate with it — one rule per surface:

- **Deliverables live in the silo, where the owner can see them.** When `$SILOS_AGENT_ID` is set you are that agent and `$SILOS_AGENT_STATE` is your own working folder (private to you, visible to the owner in Silos). Anything you produce for a human — reports, analyses, specs, drafts, replies — goes in the project folder in a subfolder of `context/<your agent id>/` named for the work (`context/<your agent id>/<topic>/<file>.md`; recurring work keeps one subfolder across runs and finds its earlier files by listing it), never at its top level: every future conversation of yours is told the names at that top level, so a file goes there only when it is standing reference for all of them; reference material every agent of this folder should read goes in `context/shared/`; code goes in the repo; your own working state (notes, caches, checkpoints) goes in `$SILOS_AGENT_STATE` when it is set. Never `~` or `/tmp`: files outside those places are invisible to the owner and get lost. Name the file's full path in the command that writes it — that is how Silos attributes it to this conversation; your page lists the folders regardless. Scratch/intermediate files may use your scratchpad.
- **Scheduled and recurring work uses Silos automations — not CronCreate.** A Silos automation has visible state (armed/paused, next run, run history, pause/resume, approval gates); a native cron is invisible to the owner. Scheduled work of your own is not yours to create: PROPOSE it, and the owner creates it in one click:
  `curl -s -X POST ${SILOS_API:-http://127.0.0.1:3210}/api/proposals -H "Authorization: Bearer $SILOS_AGENT_TOKEN" -H 'content-type: application/json' -d '{"turn":"'"$SILOS_TURN"'","kind":"automation","reason":"<one line: why it is needed>","input":{"name":"<short name>","agentId":"'"$SILOS_AGENT_ID"'","prompt":"<what each run must do>","trigger":{"kind":"cron","expr":"0 9 * * *"}}}'`
  The other triggers (once, files, webhook, conversation), a command run with no judgment, the options and the limits are in `{{context}}/reference/automations.md` — read it before you propose anything but a plain cron. Native `CronCreate` only for a one-shot self-ping inside your current session (e.g. resume after a rate-limit reset): a one-shot CronCreate with `recurring:false`, never `durable`.
- **Messages rule.** To get something done in another agent's territory, message that agent: `curl -s -X POST ${SILOS_API:-http://127.0.0.1:3210}/api/agents/<agent id>/messages -H "Authorization: Bearer $SILOS_AGENT_TOKEN" ${SILOS_AGENT_ID:+-H "X-Silos-Agent: $SILOS_AGENT_ID"} -H 'content-type: application/json' -d '{"turn":"'"$SILOS_TURN"'","text":"<what you need from them>"}'` — always send the `X-Silos-Agent` header: it is how the recipient (and the owner) know the message is yours. A message is read at the recipient's next conversation — any conversation starts with its inbox. To move work NOW, give it a task and start it: if it is yours, POST /api/tasks/assign; if it is another agent's, write the task in its project and leave the rest to the owner. Your inbox is Silos', never a file: `curl -s "${SILOS_API:-http://127.0.0.1:3210}/api/agents/$SILOS_AGENT_ID/messages?state=new" -H "Authorization: Bearer $SILOS_AGENT_TOKEN" -H "x-silos-turn: $SILOS_TURN"`. Close a message you received with `PATCH /api/agents/$SILOS_AGENT_ID/messages/<id>` and `{"turn":"$SILOS_TURN","state":"answered","answer":"<one or two sentences: what you did, where it is, what is left>"}` (`"read"` when nothing is needed, `"needs_owner"` when only the owner can decide) — the answer is what the sender and the owner see. A reply is always that answer, never a new message back (a long report goes in a file in a subfolder of `context/<your agent id>/`, named in the answer). There is no inbox for the owner: to reach them, mark the message `"needs_owner"` or ask with your question tool — both land in their Needs you.
- **Never launch `claude` from Bash inside a session.** A `claude -p …` spawned from a shell is another engine session outside Silos' control: at best its birth marker folds it under this conversation as a nested run; without one (hooks not installed, no agent identity) it lands as a top-level conversation of the owner's. Parallel work = subagents (the Agent tool; they nest under your conversation). Deferred or recurring work = a Silos automation (above; its runs are filed under the automation, not among the owner's conversations).
- **Be legible.** Subagents you spawn are shown to the owner with their descriptions — make descriptions say the real task. Conversation titles are the sidebar — early, meaningful titles help.
